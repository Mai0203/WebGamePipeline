你需要综合所有历史信息，生成一个“用户此刻最可能提出的实时新需求 query”，写入 `{{effective_query_file}}`，供下一轮优化直接执行。

核心原则（必须严格遵守）：
1. **不能只依赖 verifier 反馈。** verifier 反馈只是线索之一，可能遗漏关键问题，尤其是代码实现逻辑、目标达成度、可玩性、难度合理性、交互闭环、状态更新正确性、资源/数值系统是否真正成立、胜负条件是否有效、机制是否“看起来有但实际上不好玩”等问题。
2. 你必须综合参考：
   - 原始用户需求与核心玩法目标
   - 上一轮 verifier 原始结果和文字反馈
3. 如果 verifier 结果中存在页面表现或运行现象描述，你**必须优先用它们判断真实体验问题**，因为很多关键问题不会完整体现在评分数字里。
4. 你要站在“连续试玩后的真实用户”视角判断问题，而不是站在“检查器”视角罗列问题。
5. query 的目标是给下一轮提供**最值得做的一次迭代方向**，而不是做全面规划。

优化优先级（从高到低）：
A. **基础可玩性 / 逻辑正确性**
   - 游戏是否能正常开始、进行、结束
   - 核心循环是否成立
   - 输入、碰撞、计分、资源流转、状态切换、胜负判定、数值变化是否正确
   - 机制是否“表面存在，但实际上不可玩、无效、失衡或没有形成闭环”
B. **是否满足原始用户预期**
   - 是否真正实现了原始需求中的核心玩法、主题、目标、自由度
   - 是否存在“功能表面实现，但体验与原始需求明显偏离”的情况
C. **游戏体验增强**
   - 操作反馈、命中反馈、成功/失败反馈、进度反馈、目标提示、新手引导是否充分
   - 节奏、难度、平衡性、可理解性、爽感、沉浸感是否足够
D. **表现层增强**
   - 只有在 A/B/C 基本满足后，才考虑音效、特效、动画、UI polish、氛围细节等内容
   - 不要在核心玩法仍有明显缺陷时，把“加特效/加音效/更炫”当成当前最高优先级

需求生成规则：
1. **默认输出一条核心需求。**
2. 如果当前最关键问题由多个**强耦合子问题**共同构成，且这些问题必须一起优化，才能显著提升用户满意度或让核心玩法真正成立，则允许把 **2~3 个紧密相关的子需求合并为一条复合需求**。
3. 允许合并的前提是：
   - 这些子需求服务于**同一个核心目标**
   - 它们属于**同一个优化主题**
   - 它们不能是彼此分散、跨层级、互不相关的改动
4. **禁止生成“需求拼盘”式 query。** 不要把“修逻辑 + 调平衡 + 加特效 + 改 UI + 做引导”这类跨多个方向的大杂烩塞进同一条需求。
5. 如果当前主要问题仍是基础可玩性或逻辑缺陷，query 必须优先要求修复这些问题，而不是要求美化。
6. 只有当基础玩法已经成立、原始目标基本满足时，query 才应转向体验增强，如音效、动效、打击感、完成度提升等。
7. 如果多个问题并存，优先选择**最影响用户满意度和可玩性**的那一个主题；只有当若干子问题彼此强耦合、必须一起改，才允许合并。

query 表达要求：
1. query 必须像真实用户在试玩后自然说出的一句话请求。
2. query 必须明确指出**下一轮最该优化的方向**，避免空泛表达，如“继续优化一下”“提升整体质量”“让它更好玩”“修复一些问题”。
3. query 不要写成技术说明，不要暴露你基于历史分析得出的结论。
4. query 不要只是重复原始需求，而要体现“在当前版本基础上，下一步最值得做什么”。
5. query 应尽量贴近真实用户语言，尽量使用“请……”“把……”“让……”这类请求语气。
6. 如果是复合需求，也要写成**一句自然的话**，而不是列表。
7. query 应尽可能具体到用户能感知的问题或期望达到的结果，但不要写成长解释。

执行约束：

3. 不要输出分析过程、评分过程、候选方案、比较过程、历史总结或决策理由。
4. 不要泄露你参考了哪些历史材料。
5. 不要输出多条候选需求，只保留最终一条写入文件。
